# SQLite 主库与可选 MySQL 备份

日期：2026-10-04

## 用户确认的目标

SQLite 必须配置，始终是业务主库；MySQL 可选，只用于保存备份。
仅配置 SQLite 时只使用 SQLite；同时配置 SQLite 和 MySQL 时，业务写入 SQLite，并将已提交的数据变更同步到 MySQL。
MySQL 暂时不可用不阻止 SQLite 保存；恢复后自动补写。MySQL 不作为业务读取来源，也不自动接管 SQLite。

## 当前项目与范围

Go 后端通过 `database/sql` 使用 SQLite，连接入口为 `internal/database/sqlite.go`。
HTTP 认证、令牌、行情、汇率和业务服务都有直接数据库写入，部分使用事务。
已有资产、收入设置、退休目标的版本号触发器；业务支持预览回滚、幂等请求和审计。

备份覆盖当前全部 12 张应用表：users、sessions、api_tokens、mutation_requests、operation_logs、assets、income_settings、retirement_goal_items、exchange_rates、exchange_rate_history、market_returns、asset_history。
包含新增、修改、物理删除、归档、版本号变化及定时任务写入。
现有未提交工作保留；前端和 HTTP 请求契约不变。

## 配置和启动行为

- `DATA_DIR`：必需的 SQLite 存储配置，继续兼容现有未显式设置时使用 `./data` 的行为；数据库文件仍为 `fulibu.db`。SQLite 无法打开时服务启动失败。
- `MYSQL_DSN`：可选连接配置；为空时不连接 MySQL、不启动备份工作线程。配置错误或 MySQL 不可用时记录备份故障，业务服务仍使用 SQLite。
- 不增加 MySQL 单独运行模式，也不提供更换业务主库的选项。
- Docker Compose 默认仍只启动现有服务；提供可选 MySQL profile 和配置示例，通过环境变量连接本地或已有 MySQL。
- DSN、账户密码、备份行内容不得写入日志。

## 方案选择

推荐 SQLite 事务内持久化变更队列，后台顺序同步 MySQL。
直接在每个接口依次写两个数据库会遗漏已有直接写入路径，且进程在两次写入之间退出会丢失备份任务。
定时全量导出实现简单，但延迟较大，每次重复搬运所有历史数据，也难以准确跟踪删除。
持久化队列使 SQLite 提交和备份任务同时落盘，覆盖故障恢复与重试。

## SQLite 变更捕获

在 database 包内集中维护备份表清单、字段和主键，避免在 HTTP 层重复实现备份。
新增内部备份元数据和 outbox 表；这些内部表不镜像到 MySQL。
首次启用备份时，在同一 SQLite 事务内安装每张应用表的 INSERT、UPDATE、DELETE 捕获触发器，并将已有数据按外键依赖顺序放入队列。
该事务提交前不允许业务写入进入，保证首次全量备份与之后增量之间没有空隙。

每个队列事件包含递增序号、表标识、操作、主键及完整行数据。
INSERT/UPDATE 保存行的最终字段值；DELETE 保存主键。
行序列化保留整数精度、NULL 与文本；大金额不得经过 float64 转换。
版本号触发器可能产生多个事件；捕获最终行时不得依赖 SQLite 多触发器执行顺序，必须测试最终备份版本与主库一致。
原业务事务回滚时其队列事件也回滚，因此 dryRun 不产生备份修改。

备份初始化完成后捕获触发器持续有效；临时移除 MYSQL_DSN 只停止发送，保留新增和未发送事件，重新启用后继续补写。
未曾启用备份的 SQLite 单库实例不安装捕获触发器、不产生备份队列。
仅支持当前项目既有表结构；不会借备份功能自动升级不兼容的旧业务结构。

## MySQL 备份数据库

为当前 12 张表提供独立 MySQL DDL，保持字段、主键、唯一约束和业务数据含义。
金额、ID、版本、秒级到期时间使用可容纳 SQLite int64 的类型；小数使用相应浮点类型；文本使用 utf8mb4。
标识字段的比较规则与 SQLite 主库保持一致，避免不同大小写的键在备份端发生冲突。
时间字段保留主库值，不由 MySQL 再生成；MySQL 不安装递增版本号的业务触发器。
MySQL 显式接收 SQLite 生成的 ID，禁止分别生成 ID。
保留外键约束，并按依赖顺序初始化和应用变更。

MySQL 内部元数据记录来源实例标识及已应用的队列序号。
只允许空目标初始化，或继续同步来源标识一致的已有备份。存在无来源标识的业务数据或不同来源标识时停止同步并报告原因，避免自动覆盖其他数据库。
切换到新的空 MySQL 目标时需要显式重新全量初始化；不能沿用旧目标的队列进度。

## 同步与恢复

应用进程内仅一个备份工作线程，按事件序号顺序处理，禁止跳过失败事件继续后续写入。
每个批次在 MySQL 事务中应用事件并推进来源检查点。
插入/更新按主键写入完整行，删除按主键处理；重复应用相同事件结果不变。
只有 MySQL 事务提交成功，才清理 SQLite 中对应的队列记录。
MySQL 已提交但 SQLite 尚未确认时进程退出，重启依据 MySQL 检查点安全确认或重放，不能重复增加版本或生成审计记录。
备份数据和检查点必须一起提交；MySQL 中途失败时整批回滚。

连接或写入失败采用有上限的退避重试；待同步任务保存在 SQLite 中，应用重启后继续处理。
应用正常关闭时取消工作线程和连接；不得无限等待 MySQL 造成退出阻塞。
备份队列保留到确认成功为止，不静默丢弃；提供待同步数量、最近成功时间及最近错误的状态查询方式，不返回连接凭据或业务数据。
SQLite 自身失败时，业务请求仍遵守现有错误处理；MySQL 备份不能掩盖主库错误。

## 现有数据与使用边界

首次启用 MySQL 会备份当前 SQLite 的全部应用数据，无需用户手工逐表导入。
MySQL 备份为应用管理的实时副本；禁止外部业务同时向它写入。
备份会同步删除，因此不替代保留历史版本的离线备份。
本次不实现 MySQL 自动故障接管、MySQL 单库运行或从 MySQL 恢复 SQLite 的命令。
同一 SQLite 数据目录由一个应用实例负责备份，额外工作线程或跨进程并行发送不在本次范围内。

## 验证与完成条件

1. SQLite 单库启动及现有 Go 测试通过，接口行为保持兼容。
2. 首次启用备份时，全部 12 张表的已有数据在 MySQL 中完整保留，ID、NULL、金额、版本和时间值一致。
3. 覆盖认证、会话、令牌、资产、收入、退休目标、汇率、历史快照、幂等记录和审计的新增、更新和删除。
4. dryRun 和事务回滚不留下已提交队列任务或 MySQL 变更。
5. 验证版本触发器、外键级联删除和重复事件重放，最终两库一致。
6. MySQL 断开期间 SQLite 写入成功，待同步任务增加；MySQL 恢复及应用重启后自动补齐。
7. 验证 MySQL 提交后 SQLite 确认前中断的恢复，及目标来源冲突拒绝同步。
8. 运行 Go 单元测试、竞态检查和 vet；使用真实 MySQL 做备份集成测试。若环境不能启动 MySQL，明确报告未验证范围。
9. 更新 README、配置示例及可选 Docker 部署说明。
