# 每日行情与年化收益持久化缓存设计

## 目标与已确认策略

用户已确认：缓存各资产每日数据和当日各档年化收益；读取时补齐缺失数据；每天北京时间 09:30、17:00 更新。首屏应直接使用持久化缓存，避免先按缺省利率计算、随后才跳成历史年化结果。

“各档年化”按现有页面近 1、3、5、10 年四个区间解释。缓存持有资产对应的可获取历史行情，最长近 10 年，不采集无持仓的全市场数据。未来新增储蓄、奖金、期权兑现和定投继续只加本金，现有资产才参与年化测试。

本设计替代旧的 2026-08-03 每日市场收益缓存方案；运行环境为当前 Go 服务、SQLite 和 React 页面，不使用旧文档中的 Cloudflare Worker 调度。

## 方案选择

采用“每日原始行情 + 每日派生收益”的两层缓存。只缓存年化结果无法保存每日数据，切换区间仍依赖上游；缓存整个页面或组合预测会在持仓、收入、汇率修改后失效。组合预测继续基于当前持仓及缓存年化即时计算。

证券行情按规范化证券标识共享，避免多个账户持有同一证券时重复采集。个人持仓快照按用户和资产隔离，任何共享行情查询都不暴露他人的持仓。

## 数据模型

新增表通过加法迁移创建，不删除或重建现有业务表。新表纳入现有 SQLite 到 MySQL 的可选备份机制。

| 数据 | 唯一键与内容 |
| --- | --- |
| 每日行情 `market_daily_prices` | 规范化证券标识 + 实际行情日期 + 数据来源；币种、原始价格/单位净值、收益计算使用的复权价格/累计净值、每万份收益等适用字段、获取时间 |
| 最新报价 `market_quotes` | 证券标识；最新价、币种、实际报价时间、来源、获取时间；与已收盘的每日历史分开 |
| 年化结果 `market_returns` | 复用现有类别、代码、回溯天数、计算日期唯一键；保存四档年化、区间收益、实际起止日期、历史不足标记、计算时间和输入数据版本 |
| 历史汇率 `exchange_rate_history` | 复用现有币种、实际汇率日期唯一键；来源、获取时间；休市日期读取此前最近有效汇率 |
| 同步状态 `market_sync_state` | 证券标识、来源；已完成查询的历史范围、最早可用日期、最新数据日期、最后检查时间、数据版本、成功时间、失败信息、下次允许重试时间 |
| 个人资产日快照 `asset_daily_snapshots` | 用户 + 资产 + 上海日期；当时数量、金额、币种、估值来源和日期、获取时间；每日覆盖为最新成功状态 |
| 定时任务记录 `market_refresh_runs` | 上海日期 + 09:30/17:00 时段；运行状态、开始/结束时间、成功失败数、错误摘要 |

原始价格和复权价格不可混用。来源或算法改变时更新输入版本并使旧派生结果失效。必要的现有表新增字段要有明确迁移，并同步备份列定义。

## 历史补齐与年化计算

首次同步取得所需历史范围的每日数据。基金按上游实际分页大小遍历，不能把第一页当成完整历史；股票和 ETF 按数据源支持的范围分页或分段获取。四档收益复用同一份历史序列，避免分别下载四次。

只在成功完成某个查询范围后记录覆盖状态。非交易日没有行情行属于正常情况，不能按自然日逐日补零或无限重试。请求失败、分页中断或来源截断不能标记为完整覆盖，也不能据此断言资产成立时间不足。

读取检查请求范围覆盖情况、历史序列及所需端点汇率；对未查询范围或需要重新验证的范围补取，使用唯一键 UPSERT。已完成范围的异常缺行通过重取对应范围核对，不依赖自行猜测交易日历。

年化公式保持现有策略：`(期末收益价格 / 期初收益价格)^(365 / 实际自然日数) - 1`，结果乘 100 表示百分比。收益价格及外币历史汇率口径保持当前实现；货币基金继续按现有每万份收益算法计算，不强行套用股票公式。资金类手动利率按记录值保存，不向行情供应商查询。

回溯目标日期以最新有效历史行情日期为基准，取目标日期当天或此前最近有效数据。只有确认来源最早可用日期晚于目标日期时标记历史不足。净值晚发布、周末或节假日不等于历史不足。

每日年化既保存上海计算日期，也保存实际行情起止日期。当天计算使用昨日净值时必须保留昨日行情日期。同一天上游发布新数据或修订历史后允许覆盖当天年化；以前计算日期的结果保留，作为当时计算记录。

## 读取与页面行为

保持现有单证券和当前用户批量 `/api/market` 用法，增加缓存日期、获取时间、是否旧缓存、是否补齐中的状态。新增资产也走同一套数据服务。普通读取不修改持仓数量、手动金额或收入配置。

1. 页面本地账本响应同时提供默认近 3 年已有缓存结果，首屏直接使用缓存价和年化。
2. 当前计算日及输入版本有效时直接返回，不访问上游；切换区间优先读取数据库中的对应年化。
3. 缺失时合并相同证券的同步请求，先补原始序列和必要汇率，再计算、写入结果。
4. 有旧缓存时立即返回并注明数据日期，后台补齐；没有缓存时，资产余额照常显示，依赖缺失年化的预测显示“正在计算”，不得把未知年化默认为零来生成总预测。
5. 首次补齐可能较慢，前端以受控重试读取任务结果；不让整本账簿等待外部请求，不重复启动采集任务。
6. 缓存补齐后刷新结果；显示数据日期及更新状态，允许真实新行情带来的数值变化。

当天至少每 30 分钟允许一次轻量上游新数据检查，检查时间与行情日期分别保存。09:30、17:00 和手动强制同步不受该间隔限制。这样普通命中读取不频繁请求上游，晚间基金新净值也不会被“当天已经计算过”永久挡住。

存款、公积金、固定资产等只有用户记录的金额和利率，保存观察到的日快照；不虚构录入前的历史余额。加密资产行情仅使用已有数据源支持的能力；没有历史来源时保存当前估值并明确历史不可用，不生成假历史年化。

## 定时刷新与重启恢复

使用 Go 服务内调度器，时区固定为 `Asia/Shanghai`。新增每天 09:30、17:00 的行情刷新批次，刷新持仓证券报价、历史增量、汇率及四档年化，并保存各用户日快照。保留现有 05:00 快照和 09:16 汇率任务；它们复用缓存服务，并与新任务共用请求合并机制。

任务从未归档持仓中按证券去重，有限并发采集。SQLite 单连接不能在外部网络请求期间持有查询游标或事务。单证券失败不终止其他证券，成功结果及时落库。

进程启动后后台预热及补齐缓存，不阻塞健康检查。检查当天已到时段的任务记录，遗漏多个时段时合并执行一次当前刷新并记录补执行；已经成功的时段不重复执行。任务运行中崩溃留下的记录在重启后可恢复。

网络请求、批次及停机均有可取消上下文和超时。失败最多进行 3 次有间隔的重试，连续失败进入 5 分钟冷却，后续读取或定时批次再次尝试。手动强制刷新可越过冷却，但仍参与同证券请求合并。

## 历史修订、回退与保留

日常任务补取近期至少 30 天历史，识别上游更正；每周对已有缓存范围做一次后台完整校验，避免复权、分红修订使较早数据长期错误。新旧数据变更后使受影响年化失效并重算。手动强制刷新覆盖请求历史范围。

失败保留最后成功价格和年化，标记旧缓存及失败原因；不能写入零值或将失败结果视为成功。缺少必要外币历史汇率时不偷偷改用其他收益口径。

保留已获得的每日历史及每日年化，不随每天刷新删除。活跃采集范围最长近 10 年；已归档资产停止定时采集，历史数据保留。个人快照从首次记录开始保留。

记录批次、耗时、缓存命中/补齐、数据日期、成功失败数；日志不输出密码、会话令牌或账户余额。接口状态和日志足以区分“休市”“净值尚未发布”“同步失败”“历史确实不足”。

## 验证与验收

- 缓存命中读取不调用外部行情，服务重启后仍命中。
- 缺失范围成功补齐、重复写入幂等，失败或中断不标记完整。
- 同证券多个区间及多个账户复用采集，同用户数据隔离。
- 基金分页覆盖完整所需范围，正确区分成立不足、休市和来源截断。
- 两个上海时段、重启补执行、同日覆盖和请求合并有确定性测试。
- 历史修订使派生结果重算；必要历史汇率缺失时明确回退。
- 首屏使用数据库已有年化，没有缓存时显示计算状态，不先显示零利率预测。
- 未来新增本金不参与年化的既有测试继续通过。
- 新表迁移、备份复制和现有接口契约通过回归验证。
- 部署前备份服务数据库；部署后验证定时记录、首次预热、再次读取无上游请求及页面状态。
